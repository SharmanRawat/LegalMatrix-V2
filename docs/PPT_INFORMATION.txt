SECTION 1 — THE PROBLEM (Slide 1)
--------------------------------------------------------------------------------

CONTEXT
  - Smart India Hackathon 2026 (SIH 2026), Problem Statement PS 26034.
  - Node: Ministry of Consumer Affairs, Food & Public Distribution /
    Department of Consumer Affairs (Legal Metrology).
  - ~500 teams are competing on this PS; the demo and evidence story are what
    separate submissions.

THE FIELD PROBLEM (as the panel frames it)
  Under the Legal Metrology (Packaged Commodities) Rules, 2011 (as amended
  through 2026), every packaged commodity sold to a consumer MUST declare, on
  its principal display panel (PDP):
    1. Name & registered address of manufacturer / importer / marketer
    2. Common or generic name of the commodity
    3. Net quantity (with SI unit)
    4. Month and year of manufacture (or the "best before" equivalent)
    5. Maximum Retail Price (MRP), inclusive of all taxes
    6. Consumer care / grievance-redressal contact details
    7. Dimensions (only for non-edible goods sold by dimension)
  Enforcement is done by field inspectors who physically inspect retail
  shelves. Today this is a manual, paper-driven process: they eyeball labels,
  do mental arithmetic on MRP vs. unit-sale-price violations, and hand-write
  reports that are hard to defend later in adjudication.

WHY IT IS HARD
  - Labels are noisy: glossy curved packaging, tiny fonts, watermarks, mixed
    Hindi/English, Devanagari, mangled OCR tokens ("R110.00" for a ₹7 MRP).
  - Violations are subtle: MRP can be printed but the label violates because
    the container's net content is filled below declared quantity, or the MRP
    is not inclusive of taxes.
  - Enforcement needs EVIDENCE: a report that quotes the exact label text,
    shows the photograph, and survives legal challenge — not just a verdict.

SLIDE-READY COPY (heading + 3 bullets)
  Title: LegalMatrix — AI Legal-Metrology Inspection for Packaged Commodities
  • SIH 2026 · PS 26034 · Ministry of Consumer Affairs (Legal Metrology)
  • Field inspectors photograph a product label with a phone; the platform

SECTION 2 — THE SOLUTION & HOW IT WORKS (Slide 2)
--------------------------------------------------------------------------------

WHAT LegalMatrix IS
  An end-to-end "inspect → evaluate → evidence" platform:
    1. Inspector captures 1–3 photos of the product label (browser or PWA).
    2. CPU OCR (RapidOCR / PP-OCRv3, ONNX) reads the label text with word
       boxes and per-word confidence.
    3. A small on-device LLM classifier (Ollama qwen2.5:3b) maps the OCR lines
       to the declaration fields, merged with regex extraction for structured
       fields (MRP, net quantity, dates, consumer care).
    4. The compliance rule engine evaluates the extracted declarations against
       the codified 2011 Rules → status (COMPLIANT / POTENTIAL_VIOLATION /
       REVIEW_REQUIRED) + an evidence-backed score.
    5. Outputs: web report, PDF with embedded evidence photos, JSON/CSV
       exports, a compliance certificate with a QR code whose payload can be
       publicly verified, and an "Evidence Planner" that lists what evidence is
       still needed for a defensible decision.

THE 10 FROZEN FIELDS THE PIPELINE EXTRACTS
  mrp, usp (unit sale price), net_quantity, product_name, manufacturer,
  manufacturing_date, expiry_date, consumer_care, dimensions, edible (flag).

PLUS AN 11TH DERIVED FIELD — manufacturer_address (side channel)
  A deterministic maker-address extractor (manufacturer_address.py) reads only
  the raw OCR token stream, scores each token for address salience (6-digit
  PIN codes + street/city/office markers; licence-number digit runs excluded
  as PIN impostors), groups the winners into visual runs by y-proximity, and
  injects the best PIN-bearing run into declarations right after
  `manufacturer` — e.g. "Amul Fed Dairy, Anand 388001". It is report/evidence
  and instructor-editable, but by design NEVER modifies the frozen ten fields
  or the compliance pipeline (the golden-statutory audit stays byte-identical).

  IMPORTANT for Q&A: the derived address does NOT change the compliance
  score. The Rule 6(1)(a) presence check and `missing_declarations` only read
  the `manufacturer` value, so a label whose name extracts without its
  address still scores full weight on that rule. The address is an evidence/
  transparency enhancement, not a scoring input.

  WHY it is not a scoring input (be ready to explain this):
  • The score is passed/7 — each of the 7 rules maps to exactly one frozen
    field; the address channel has no slot in that evaluation by design.
  • The merged `manufacturer` value usually already embeds the address
    (e.g. "…Regd. Office: …"), so Rule 6(1)(a) absorbs it indirectly —
    a second gate would count the same evidence twice.
  • The extractor is a heuristic (PIN + street/city markers on raw OCR
    tokens) that can miss valid addresses (no PIN, back-panel placement,
    foreign formats). Letting a miss reduce the score would flag legal
    labels as non-compliant — against the "never fabricate a verdict" rule.
    So misses are surfaced as evidence + a visual-verification hint instead.
  • Keeping it out of scoring preserves the golden-statutory audit bit-for-bit
    (the side-channel contract in manufacturer_address.py).
  If the address should ever gate the rule, it needs benchmarked precision
  across the 70+ photo corpus first, then a validated weight.

CPU-FIRST DESIGN DECISION (judge bait — put this on the slide)
  - The whole inference pipeline runs on a field inspector's laptop with NO
    GPU: RapidOCR (PP-OCRv3, ONNX) + qwen2.5:3b classifier. Demo and
    submission run entirely on this CPU path.
  - Users only need a browser/PWA — no model download, no mobile compute.
  - An optional Qwen2.5-VL (qwen2.5vl:7b) vision-model rescue exists for hard
    labels but is OFF by default — proof the core works without a GPU.

SECTION 4 — THE COMPLIANCE ENGINE & SCORING (Slide 4)
--------------------------------------------------------------------------------

THE 7 REQUIRED DECLARATIONS (directly traceable to the Rules — put the table
on the slide or use the 7 numbered items)
  1. manufacturer_name_address — Rule 6(1)(a) — CRITICAL — name + registered
     address of manufacturer/importer/marketer on the PDP
  2. generic_commodity_name — Rule 6(1)(b) — CRITICAL — common name
     ("Honey", "Sunflower Oil") prominent on PDP
  3. net_quantity — Rule 6(1)(c) — CRITICAL — numeric + SI unit (g/kg/ml/L;
     cm/m for length); liquids declared at 20 °C
  4. month_year_manufacture — Rule 6(1)(d) — HIGH — month + year (MMM/YYYY,
     MM/YYYY, MM/YY)
  5. mrp — Rule 6(1)(e) — CRITICAL — "MRP Rs.XX / MRP ₹XX", inclusive of all
     taxes; must contain a digit + currency symbol (₹ / Rs. / INR)
  6. consumer_care_details — Rule 6(2) — HIGH — name+address+email and/or
     phone; a contact channel (@ / toll free / 1800 / 10–12 digit) required
  7. dimensions_where_relevant — Rule 6(1)(f) — MEDIUM — only for non-edible
     goods sold by dimension; auto-skipped for edible products

BEHAVIOUR
  - Missing declaration → violation, status MISSING.
  - Present but malformed → FORMAT_ISSUE (severity MEDIUM).
  - Score = passed/7 × 100 (dimensions counts only when relevant).
  - Truth, never fabrication: anything unmeasurable is honestly reported as
    REVIEW_REQUIRED / CANNOT_MEASURE — the platform lists what evidence is
    still needed instead of inventing a verdict.

5-AXIS RADAR SCORING (current committed weights)
  Declarations 0.375 · Pricing 0.25 · Dates 0.125 · Consumer Care 0.125 ·
  Readability 0.125 (OCR confidence/legibility proxy = avg word confidence)
  Overall grade (A/B/C/D) and radar recomputed from live inspection data; the
  live demo inspection produced grade A, overall 97.5, COMPLIANT 7/7.

PRICING ENGINE (USP / MRP checks — Rule math)
  - compute_unit_sale_price, validate_usp with tolerance, USP exemptions,
    unit extraction ("per 100 g" conversions), rounding rules.
  - Misleading-declaration heuristics flag MRP-vs-USP mismatches and
    net-quantity/price inconsistencies.

SECTION 7 — FONT-SIZE MEASUREMENT (DIFFERENTIATOR — STATUS: LIVE & VALIDATED)
--------------------------------------------------------------------------------
IMPORTANT CONTEXT FOR THE DECK
  This feature is the strongest differentiator vs. the ~387–500 competing
  submissions. It was removed once for submission-safety review, then restored
  and VALIDATED on real field photos (Sept 2026): a barcode-calibrated
  measurement of a real product label produced a genuine COMPLIANT verdict
  (1.96 mm measured vs 1.0 mm required, ±0.29 uncertainty) and a scored
  Font Size radar axis (weight 0.20, grade A, overall 94.4). When no usable
  reference (card/barcode/EXIF) is in the frame, it honestly reports
  CANNOT_MEASURE and the axis weight drops to 0 — the score never pretends
  fine print was verified.
  The project's governing rule: never fabricate a measurement — an
  uncalibrated image is reported as CANNOT_MEASURE / REVIEW_REQUIRED.

WHAT IT DOES
  Measures the PHYSICAL height of the declaration text on the label (letters
  and numerals) in millimetres and checks it against the minimum font heights
  prescribed by the Legal Metrology (Packaged Commodities) Rules, 2011 —
  catching an entire class of violations (fine-print labels) that pure OCR
  extraction cannot see.

THE CALIBRATION CHAIN (scale_calibrator.py) — pixels → millimetres
  1. credit_card — a credit/debit card photographed beside the product is
     ISO/IEC 7810 ID-1: 85.60 × 53.98 mm, an exact, traceable pixels-per-mm
     reference (aspect ~1.586, detection tolerances: aspect 1.30–1.90, area
     1.5–65% of frame, angle ≤ 18°, uncertainty ±6%). A hand-made cardboard
     card of the same dimensions satisfies this rung.
  2. barcode — product barcode (20.0 mm nominal width) as a coarser
     reference; magnification not fixed → higher uncertainty (±15%).
  3. exif — camera-metric estimate from phone EXIF (35 mm-equivalent focal
     length → horizontal FOV, + SubjectDistance); uncertainty ±20%, PPM
     bounds 1.0–300.0.
  4. None usable → measure() returns CANNOT_MEASURE with an auditable reason.
     We never fabricate a figure from an uncalibrated image.

MEASUREMENT (font_measurement.py)
  - New pipeline: each OCR token's pixel height → mm via the calibration
    reference → compare against the rule minimum.
  - Legacy VLM path: CAP-HEIGHT of glyphs inside a text-region box (vertical
    height of the dominant capital/digit stroke cluster, so descenders do not
    inflate the reading).
  - Fallback heuristic (component heights in the lower half of the image) is
    UNVALIDATED → always reported as REVIEW_REQUIRED (informational only,
    never an automated verdict).
  - Defensibility gates: geometric + glyph sanity checks per box/token; a
    measured mm outside [0.3 × required, 10.0 × required] is implausible and
    forces REVIEW_REQUIRED; rejected calibrations carry a reason string.

THE REGULATORY THRESHOLDS (font_size_requirements in rules.json)
  Letters (normal / embossed): 1.0 / 2.0 mm
  Numerals on weight/volume declarations (by net quantity):
    ≤ 200 g/ml → 1.0 / 2.0 mm · 200–500 → 2.0 / 4.0 mm · > 500 → 4.0 / 6.0 mm
  Numerals on length/area/number declarations (by PDP area):
    ≤ 100 cm² → 1.0 / 2.0 mm · 100–500 → 2.0 / 4.0 mm · 500–2500 → 4.0 / 6.0 mm
    · > 2500 cm² → 6.0 / 6.0 mm

SCORING IMPACT
  Restores the 6-axis radar (Declarations 0.30 · Pricing 0.20 · Dates 0.10 ·
  Consumer Care 0.10 · Font Size 0.20 · Readability 0.10). When no
  calibration reference exists, the Font Size axis weight drops to 0 and the
  overall score is re-weighted across the axes that ARE measured — the score
  never silently pretends fine print was verified.
